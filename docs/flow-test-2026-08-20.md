# 全链路实测记录：2026-08-20

## 1. 实测范围

职位搜索采集 → 职位导入 → 生成投递包 → 二次确认 → 试运行投递。

测试账号：BOSS直聘（Cookie 已加密保存，登录状态正常，页面显示已登录求职者账号）。
测试职位：`job_id=17`，`application_id=5`，真实 BOSS 职位详情页。

## 2. 实测结果

### 2.1 可以走通的部分

1. 搜索采集：可成功返回 20 条深圳职位，但非稳定，连续多次触发后会被 BOSS 安全验证拦截。
2. 职位导入：正常写入数据库。
3. 生成投递包：`POST /api/jobs/17/packet` 成功，DeepSeek 生成针对性打招呼语，生成 `application_id=5`。
4. 二次确认：`POST /api/applications/select` 成功，状态为 `confirmed`。

### 2.2 走不通的部分

试运行投递失败，错误已从模糊的“未找到输入框”修正为：

```text
平台安全脚本将页面重置为空白页，通常表示自动化操作被识别，请稍后重试或改用真实浏览器登录态
```

失败过程：受控浏览器打开 BOSS 职位详情页后进入
`/web/passport/zp/security.html`，随后反复重定向，最终回退到 `about:blank` 或 BOSS 首页，职位详情和打招呼输入框均未出现。

## 3. 根因分析

- BOSS 当前使用 `disable-devtool` 类反调试检测，并通过 CDP 会话、`console.table`、`performance.now` 时间差等手段判断是否被自动化控制。
- 检测命中后执行惩罚：刷新、跳转 `about:blank`、清空页面、触发安全验证。
- 该问题并非本项目特有。`loks666/get_jobs` 的 README 与讨论 #250 明确记录了同样现象：首页可访问，投递详情页不断刷新回退。
- 实测还发现：搜索页有时能通过，职位详情页几乎每次被拦截；风控为间歇性，与频率、Cookie 会话、浏览器指纹有关。

## 4. 已做的代码修复

1. `backend/app/adapters/base.py`：安全验证等待逻辑不再只依赖 `body.inner_text()`，同时识别 `security.html`、`_security_check=`、`about:blank`，并返回明确错误和截图路径。
2. `backend/app/services/job_scraper.py`：搜索流程同样识别安全页与空白页回退，返回 `page_url` 便于排查。
3. `backend/.env`：`BROWSER_HEADLESS=false`，投递/搜索使用可见浏览器，便于用户手动完成平台验证。

### 实测过的反检测方案

- Playwright 普通受控浏览器：被拦截。
- 真实 Chrome + CDP 连接：被拦截。
- patchright：被拦截。
- 社区 anti-hook 脚本（覆盖 `console.table` / `performance.now`）：可避免直接回退 `about:blank`，但仍被重定向到首页，无法进入职位详情。

结论：BOSS 当前的风控是多层对抗，单一反检测方案不能保证稳定通过，且社区最活跃的同类项目也尚未解决投递详情页回退问题。

## 6. 建议

1. 不建议现在切换到其他完整项目，也不建议从零重写；保留当前工作台，重点改造投递执行层。
2. 最稳的 MVP 采用“半自动辅助投递”：系统负责搜索、筛选、生成打招呼语、组织投递队列，最终打开真实浏览器页面并复制/填入打招呼语，由用户点击发送。
3. 若坚持全自动投递，下一步优先验证 `Camoufox`、`nodriver`、`obscura` 或 `boss-helper` 扩展；但需接受账号风控风险，且不能保证长期稳定。
4. 继续遵守边界：不做接口逆向，不绕过验证码，真实投递必须二次确认，投递间隔保持 40 秒以上。
